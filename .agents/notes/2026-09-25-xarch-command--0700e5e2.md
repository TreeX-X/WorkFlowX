# xarch architect-workspace scaffold command

## Problem

Architect workspaces carry repository identity and initiative Notes. A scaffold outside the shared Note directory is invisible to the project projection. Guessing a checkout from its name can bind a module to the wrong source; configuration drift lets different agent surfaces produce incompatible workspaces.

## Decision

The xarch command runs directly in the main agent. Its ordered steps are Git initialization, repository identity, flat .agents/notes/ initiative declarations, optional CODEOWNERS and README, workspace.create registration, and projectView verification. Existing identity is verify-only, dirty repositories stop, and unsuccessful registration remains pending. The project and confirmed modules use fresh UUIDs, module parent URIs, and the pinned S1.2 Goal, Scope and Acceptance criteria sections. With no confirmed module boundaries, the scaffold contains only the project. Optional instructional declarations carry architecture:example and stay out of current structure.

Repositories and interfaces use the formal optional fields only when known. Composition binds repoId, checkoutId, path and selected explicitly in .agents/.local/workspace-map.json. The command never infers a checkout from a title or directory name. Module splits, interface providers and primary bindings use confirmed conversation choices; unresolved choices follow the existing approval flow, and subsequent Note changes use expectedHash and harness transactions.

The [module convention](../../.codex/skills/noteX/module-structure.md) distinguishes project and module initiatives by exact tags and limits current structure to accepted declarations. Every declaration has one owning repository. Decisions retain reasons and Tasks retain delivery contracts. Development workflows read relevant boundaries and synchronize declarations only when module existence, responsibility, public interfaces, explicit dependencies or recorded entrypoints change. Unavailable or unauthorized owning repositories leave concrete pending synchronization in existing results. Hard interface constraints enter existing task scope and acceptance with fixed references; ordinary context adds no per-task binding or additional report.

Both orchestrateX surfaces and the Claude command are managed by sync-harness-rules. The shared standard and digest stay pinned; templates consume that standard without defining new kinds, fields or views.

## Alternatives considered

- Prompt-assembled establishment — strongest case is zero new files, but steps get skipped and identities overwritten with no verifiable gate; rejected in favor of the deterministic command with per-step checks.
- Full bus-payload delegation mode — strongest case is uniformity with xdel/xflow, but scaffolding has no task note, no dispatch target, and no iteration; a payload contract would be empty ceremony, so xarch stays direct like xdo.
- Do nothing / reuse — keep hand-building workspaces; rejected because unrepeatable setup is exactly where shared-project identity corruption starts.
- Mandatory example components offer immediate visual content, but an instructional node can be mistaken for real architecture. Explicit example tags and confirmed-only scaffolding preserve useful templates without asserting invented boundaries.
- A new module kind offers dedicated validation, but existing initiative fields already describe hierarchy and interfaces. The authoring convention avoids a sealed-standard revision; a dedicated kind merits reconsideration when module-specific validation requires it.

## Consequences

- **Gains**: every architect workspace starts from the same six verified steps on both surfaces; sync tooling converges adopters without a standard release.
- **Costs and limits**: scaffolding requires host registration and projection capabilities; unavailable registration remains an explicit pending step. Managed synchronization must preserve local configuration. Revisit when another host requires a different registration contract.
- Module facts require maintenance when structure changes. Opt-in tags leave historical initiatives outside the current graph until deliberately classified; consumers must expose unresolved ownership and planned declarations without inventing connections. The convention and both template surfaces are verified by standard and synchronization checks, with templates parsed through the installed S1.2 harness-core.
