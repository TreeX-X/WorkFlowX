# Execution Persistence

Task Notes and `.agents/evidence/<receipt-id>.json` are the portable execution assets in the task's primary repository. Local runs, leases, conversations and recovery journals under `.agents/.local` are checkout-specific coordination data. A reader reconstructs historical results and coverage without those local records; it must not infer ownership of a running task from their absence.

The execution host updates only the task's `execution` metadata through a managed write with an exact file hash and a matching previous execution state. These updates preserve unrelated YAML, body text and the task contract hash. Model file tools do not receive unrestricted access to `.agents`. Each state change checks the local run revision; a stale writer must reload. A second prepare cannot replace an existing task execution, including terminal history.

Writing a receipt, its task reference and the local run snapshot is one recoverable asset operation under the checkout's note lock. Durable after-images and a journal precede target changes. Readers settle pending transactions before publishing results. Recovery resumes only when every target has its recorded before or after bytes; foreign bytes require explicit recovery and are never overwritten. Retrying the same receipt ID with the same content is idempotent; different content is a conflict. Historical failure receipts remain available.

Receipt content identity is SHA-256 of UTF-8 compact JSON with object keys recursively sorted in Unicode code-point order. Arrays retain order; all scalar values, including string whitespace and checkbox-like text, remain unchanged. JSON indentation, object key order and file LF/CRLF do not change this digest. This digest also supplies `dependencies[].receiptHash`. Code manifests continue to hash raw file bytes. The fixed receipt-content fixture pins this distinction.

A task-linked receipt contributes coverage only when the task records `done`, references the receipt and matches its mode and attempt. Validity rechecks the current contract, inputs, acceptance criteria, declared checks and code. Failed or orphan receipts never imply completion. Current Git-visible scope additions invalidate an older manifest; deleted entries remain verifiable after deletion is committed. A valid receipt and a satisfied closeout policy are separate results.

For `commit-required`, closeout searches only commits reachable from the selected checkout's HEAD. One candidate tree must contain a valid completed task with the same semantic contract, an identical receipt content digest and every tested file as raw bytes (or absent for a deleted entry). The current worktree and live inputs must also remain valid. A commit on an unrelated branch, code-only commit, absent receipt, or cached result without revalidation cannot establish landing. Explicit checks may examine earlier candidates when HEAD differs. `working-tree-authorized` requires its authorization reference and never claims a commit.

Read-only shares may include selected Notes and their referenced formal receipts. They exclude leases, local run IDs, machine paths and conversations. A receiving host must validate evidence against its own checkout; inclusion in a share does not establish validity or execution ownership.

Validation covers interrupted writes, duplicate receipt conflicts, stale concurrent writers, retained foreign edits, real command execution, raw binary and deleted files, current-branch reachability, receipt layout changes, and reconstruction in a fresh checkout. Real model and desktop integration remain separate host acceptance checks. This candidate specification does not activate a standard cutover.
